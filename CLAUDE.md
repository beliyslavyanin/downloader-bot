# CLAUDE.md

Этот файл — инструкции для Claude Code при работе в этом репозитории.

## О проекте

Телеграм-бот для скачивания видео: пользователь присылает ссылку (VK, Telegram-посты,
X/Twitter, YouTube, TikTok, Instagram), бот скачивает видео и отправляет его в чат.

Бот **публичный** (доступен всем в Telegram), нагрузка на старте небольшая, но нужно
закладываться на непредсказуемых/неаккуратных пользователей — см. раздел «UX и защита
от дурака».

Архитектура: **монолит на asyncio**, один процесс. Подробности — в [architecture.md](architecture.md).
Если нагрузка вырастет, миграция намечена на архитектуру с очередью задач (Redis + воркеры) —
не реализовывать заранее, только если реально понадобится.

## Стек

- Python 3.11+
- aiogram 3.x (асинхронный Telegram bot framework)
- yt-dlp (скачивание видео со всех поддерживаемых платформ)
- Стандартный `asyncio` + `concurrent.futures.ProcessPoolExecutor` для параллельных закачек
  (yt-dlp — блокирующий/CPU-bound, в event loop не вызывать напрямую)

Не добавлять Celery/Redis/очереди без явного запроса — это следующий этап архитектуры,
не текущий.

## Ключевые ограничения платформы

- Обычный Telegram Bot API отдаёт/принимает файлы **до 50 МБ**. Если видео больше —
  бот обязан сообщить об этом пользователю *до* скачивания (по метаданным yt-dlp), а не
  скачивать зря и потом упасть на отправке.
- Если в будущем понадобится слать файлы больше 50 МБ — потребуется поднимать
  Local Bot API Server (до 2 ГБ). Это отдельное инфраструктурное решение, не делать неявно.
- Скачивание с YouTube формально нарушает ToS площадки — бот для личного/некоммерческого
  использования, не оптимизировать под обход блокировок или массовую нагрузку.

## UX и защита от дурака (обязательно для любой фичи)

Целевой пользователь — тот, кто не читает подсказки и будет слать что угодно. На каждом
шаге обработки ссылки пользователь должен получать понятную обратную связь:

1. Валидация ссылки на входе (домен/формат) — сразу сказать, если платформа не
   поддерживается или это вообще не ссылка.
2. Статус-сообщения по ходу обработки: принял → скачиваю → отправляю → готово/ошибка.
   Пользователь не должен гадать, завис бот или работает.
3. Проверка размера/длительности видео по метаданным **до** полного скачивания.
4. Rate-limit на пользователя (кол-во активных задач и запросов в минуту) — сообщать
   об этом явно ("подождите, у вас уже есть активная загрузка"), не молча дропать.
5. Таймаут на скачивание с понятным сообщением, а не зависание бота.
6. Все ошибки yt-dlp/сети переводить в понятные фразы на языке пользователя
   (приватное видео, видео удалено, регион-лок и т.п.) — никогда не отдавать сырой traceback.

## Файлы и временное хранилище

Кэша нет: скачал → отправил → удалил. Гарантированная очистка временных файлов
даже при ошибке отправки (try/finally или контекстный менеджер), никогда не оставлять
мусор на диске VPS.

## Соглашения по коду

- Без преждевременных абстракций: если поддерживается 5 платформ через один и тот же
  yt-dlp-вызов — не создавать отдельный класс-стратегию на каждую платформу без причины.
- Комментарии — только там, где решение не очевидно из кода (например, почему используется
  ProcessPoolExecutor, а не просто await).
- Конфигурация через переменные окружения (токен бота, лимиты) — не хардкодить.
