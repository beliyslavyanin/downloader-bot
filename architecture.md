# Архитектура

Статус: выбран вариант **«Монолит на asyncio»** (один процесс, без внешних брокеров
очередей). Причина выбора и альтернативы — см. «Рассмотренные варианты» внизу файла.

## Компоненты (все внутри одного процесса)

```
Telegram ──▶ Update Handler (aiogram)
                 │
                 ▼
           URL Validator            — домен/формат ссылки, whitelist платформ
                 │
                 ▼
           Rate Limiter             — лимит активных задач и запросов/мин на юзера
                 │
                 ▼
           Download Semaphore       — asyncio.Semaphore(N), ограничивает
                 │                    одновременные закачки на всю VPS
                 ▼
           Metadata Probe (yt-dlp, --skip-download)
                 │
                 ▼
           Size/Duration Guard      — если больше лимита Telegram, сообщить и выйти,
                 │                    не скачивать
                 ▼
           ProcessPoolExecutor      — воркер-процесс запускает yt-dlp и реально
                 │                    качает файл во временную директорию
                 ▼
           Sender                   — отправляет файл в чат, чистит temp-файл
                                       в finally независимо от результата
```

Все шаги — часть одного Python-процесса; параллелизм между пользователями обеспечивается
корутинами aiogram + ограниченным пулом процессов под тяжёлую CPU/IO-работу yt-dlp.

## Поток обработки одной ссылки

1. Пользователь присылает сообщение → aiogram handler получает апдейт.
2. **URL Validator**: regex + whitelist доменов (vk.com, t.me, x.com/twitter.com,
   youtube.com/youtu.be, tiktok.com, instagram.com). Не проходит — мгновенный понятный ответ, обработка
   не начинается.
3. **Rate Limiter**: проверка, что у пользователя нет уже активной задачи и не превышен
   лимит запросов в минуту. Не проходит — сообщение с объяснением, задача не ставится.
4. Бот отправляет статус-сообщение "Принял ссылку, проверяю видео..." и **редактирует**
   его по мере продвижения (не спамит новыми сообщениями на каждый шаг).
5. Задача забирает слот в `asyncio.Semaphore(MAX_CONCURRENT_DOWNLOADS)` — если слотов нет,
   статус меняется на "в очереди, ждите" вместо тихого зависания.
6. **Metadata Probe**: yt-dlp с `--skip-download`/`extract_info(download=False)` в
   executor'е (чтобы не блокировать event loop) — получить размер и длительность.
7. **Size/Duration Guard**: если оценка веса файла превышает лимит Telegram (50 МБ) —
   сообщить пользователю и остановиться, не скачивая.
8. Реальное скачивание запускается в `ProcessPoolExecutor` (отдельный процесс на задачу,
   ограничен тем же семафором/пулом) во временную директорию, уникальную для задачи.
9. По завершении — **Sender** отправляет файл в чат. Независимо от успеха/ошибки —
   `finally` удаляет временный файл и директорию.
10. Ошибки на любом шаге (сетевая, yt-dlp exception, таймаут) перехватываются и
    переводятся в человеко-читаемое сообщение; сырые исключения в чат никогда не уходят,
    только в лог.

## Параллелизм и защита ресурсов VPS

- `MAX_CONCURRENT_DOWNLOADS` — общий лимит одновременных скачиваний на процесс
  (защищает CPU/диск/сеть VPS от перегрузки).
- Лимит активных задач на одного пользователя (обычно 1) — защищает от того, что один
  человек займёт весь пул параллельных слотов.
- Таймаут на каждую задачу (metadata probe + скачивание) — если сайт не отвечает,
  задача принудительно завершается и слот освобождается, а не висит вечно.
- Все лимиты настраиваются через переменные окружения, не хардкодятся.

## Временные файлы

- Каждая задача скачивает файл в собственную временную директорию с уникальным именем.
- Очистка гарантирована через `try/finally` (или context manager) на уровне задачи —
  срабатывает и при успехе, и при ошибке, и при таймауте/отмене.
- Кэша нет — повторная ссылка скачивается заново.

## Конфигурация (переменные окружения)

| Переменная | Назначение |
|---|---|
| `BOT_TOKEN` | Токен Telegram-бота |
| `MAX_CONCURRENT_DOWNLOADS` | Размер пула одновременных закачек |
| `MAX_FILE_SIZE_MB` | Порог, после которого видео не скачивается (по умолчанию 50) |
| `DOWNLOAD_TIMEOUT_SEC` | Таймаут на metadata probe + скачивание одной задачи |
| `RATE_LIMIT_PER_USER_PER_MIN` | Сколько запросов в минуту разрешено одному пользователю |
| `MAX_DURATION_SEC` | Максимальная длительность видео (по умолчанию 3600) |
| `MAX_VIDEO_HEIGHT` | Максимальное разрешение по высоте, чтобы чаще влезать в лимит размера (по умолчанию 720) |
| `UPLOAD_TIMEOUT_SEC` | Таймаут отправки файла в Telegram (по умолчанию 300) |
| `MAX_ACTIVE_TASKS_PER_USER` | Сколько одновременных задач у одного пользователя (по умолчанию 1) |
| `TEMP_DIR` | Директория для временных файлов |
| `COOKIES_FILE` | Необязательный cookies.txt (Netscape) для yt-dlp; каждая задача работает с временной копией |

## Деплой

- Один процесс на VPS, запуск через systemd unit (auto-restart при падении).
- Логи — в stdout/journald, без сырых стектрейсов в Telegram.
- При падении процесса все незавершённые задачи теряются — пользователь увидит
  зависший статус; это принятый компромисс монолита (см. ниже).

## Рассмотренные варианты и почему выбран этот

1. **Монолит на asyncio (выбран).** Минимум инфраструктуры, быстро деплоится и
   отлаживается, достаточно для небольшой нагрузки на старте. Минусы: при падении
   процесса теряются активные закачки, масштабирование только вертикальное (апгрейд VPS).
2. **Бот + очередь задач (Redis + RQ/Celery/arq) + пул воркеров.** Более устойчиво
   к абьюзу и падениям, горизонтально масштабируется. Отложено как следующий шаг —
   избыточная инфраструктура для текущей нагрузки.
3. **asyncio-бот + ProcessPoolExecutor без брокера.** Промежуточный вариант между 1 и 2.
   По сути частично включён в выбранную архитектуру (см. компонент ProcessPoolExecutor
   выше) — используется как механизм параллелизма внутри монолита, а не как отдельная
   архитектура.

### Триггеры для миграции на вариант 2

Пересмотреть архитектуру в сторону очереди задач, если:
- Один процесс регулярно не успевает обрабатывать очередь (пользователи подолгу ждут).
- Нужна отказоустойчивость — падение бота не должно ронять уже начатые закачки.
- Нужно горизонтальное масштабирование на несколько машин.
